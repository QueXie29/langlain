# 面向初级 Python / AI 应用岗位的项目提升路线

根据 2026-11-11 提供的三份岗位截图，以及本仓库代码的静态阅读整理。下文区分已有实现和建议实现；没有重新运行应用、执行测试或调用收费模型，不代表已验证运行质量。技术依据见 [官方来源核对笔记](JUNIOR_RAG_UPGRADE_SOURCES.md)。

建议把项目目标定为：**能够持续更新文档、给出可核对的答案、用实验衡量质量，并能部署和排查问题的多用户知识库助手。** 完成后，再增加一个范围明确的工具调用场景，覆盖 Agent 岗位要求。

三份招聘材料共同看重 Python 基础、Web/API 开发、数据处理、代码可维护性、测试和排障。第二份更强调 HTTP、Redis、MQ 及 AI 编程工具；第三份明确列出 Agent、工具调用、Prompt 与评测。学历、毕业年份和经验要求需要另外核对，不能用项目功能替代。

**1. 当前已经具备的能力**

| 能力 | 代码证据 | 需要进一步证明什么 |
| --- | --- | --- |
| Django REST API、注册登录、JWT、Vue 界面 | `backend/knowledge/views.py`、`frontend/src/` | 能解释请求、鉴权、刷新、异常码和前后端联调 |
| PDF / DOCX / TXT / Markdown 解析及文本清洗 | `services/parsers.py`、`services/chunking.py` | 解析结果是否保持阅读顺序、表格含义和来源位置 |
| 中文分隔符递归切块 | `services/chunking.py` | 当前 800 字符 / 120 字符重叠对业务语料是否合适 |
| 文档与问题分别向量化、维度与返回顺序校验 | `services/qwen.py` | 批量吞吐、耗时、失败恢复及版本变化的处理 |
| PostgreSQL / pgvector、按用户与模型配置过滤 | `models.py`、`services/retrieval.py` | 数据量增长后的查询计划、耗时和召回质量 |
| 默认 20 个候选经过重排序，最多取 5 个 | `services/retrieval.py` | 重排序相对不重排的收益及额外延迟、用量 |

| 后端测试，包括真实 pgvector 测试文件 | `knowledge/tests/` | 持续运行的 CI；SQLite 模式会跳过 pgvector 测试 |

现有项目已经超出一个单文件问答 demo。最需要补的是质量证据、完整的数据生命周期和交付能力。

**2. 先选一个可以验收的使用场景**

保留当前知识库产品，选择一种固定语料，例如软件产品手册、API 文档和常见故障说明。先准备约 10–20 份可公开演示的资料，包含专有名词、错误码、操作步骤、表格、跨章节问题，以及文档没有答案的情况。

产品验收从用户行为出发：上传资料后能看到处理进度；问题有答案时能定位出处；没有依据时明确拒答；修改文档后能更新索引；接口失败后能恢复；其他账号无法读取这份资料。样本数量是个人项目的起步建议，不是招聘方的统一门槛。

**3. 第一优先级：建立评测与排障闭环**

先人工整理 30 条问题建立基线，随后扩充至约 100 条。每条记录建议包含：问题、问题类别、可否回答、参考答案、必要证据所在文件版本和页码/章节，以及原文证据。切块参数会变化，因此金标不要只绑定本轮生成的 chunk ID。

可采用以下类别：单段直接问答、同义改写、错误码/专有名词、表格数值、跨章节/跨文档、追问、无答案，以及用户隔离与文档中恶意指令等安全回归案例。业务质量评测和权限测试分别统计。

为开发调参和最终验收保留不同的问题集，同一事实的近似改写尽量放在同一组，避免反复调阈值后把验收题记住。语料和文件版本要固定并记录。

| 指标 | 口径与用途 |
| --- | --- |
| Hit@5 | 有答案的问题中，前 5 个结果至少命中一条标注证据的比例；不能代替完整证据覆盖率 |
| Recall@K | 前 K 个结果覆盖的必要证据数 / 全部标注必要证据数；跨文档题尤其需要 |
| MRR | 首条有效证据排名的倒数，在可回答题上取平均 |
| 答案正确性 | 对照参考答案，使用固定评分准则人工检查 |
| 事实与引用支持情况 | 分别检查答案事实是否有依据、标出的引用是否支持对应事实 |
| 无答案题拒答率 | 无答案题中正确拒答的比例 |
| 有答案题误拒率 | 有答案题中被错误拒答的比例；需要与上一项一起看 |
| P50 / P95 耗时 | 分别记录向量化、召回、重排、生成和总请求耗时，注明样本数与并发 |
| 模型用量 | 能获取时记录输入/输出 token、请求次数和单次问答费用；拿不到就明确标注未知 |

先运行现有“向量召回 + 重排”作为基线，再加入“仅向量”“混合召回”“混合召回 + 重排”等对照。每次尽量只变一个因素，例如切块大小或召回方式；比较时固定生成模型、Prompt、语料和问题集。少量样本的 P95 只能作为观察值，不能宣称线上服务水平。

LLM 评分可以辅助筛查，但要抽样人工复核；模型给出的高分不能直接当作答案正确率。RAG 的检索质量、答案正确性和依据一致性应该分别评估，参考 [LangSmith 官方 RAG 评测教程](https://docs.langchain.com/langsmith/evaluate-rag-tutorial)。

增加请求 ID、阶段耗时、候选 chunk ID、两种排序分、模型/索引/Prompt 版本和错误分类。日志默认记录定位问题所需的元数据，避免把全部用户原文当普通日志长期保存。

建议新增 `evals/` 和一个评测管理命令，输出 JSON/CSV 与 Markdown 对比报告；这是建议结构，目前尚未创建这些实现。

验收：能用同一批问题复现实验，并把失败归到“没解析出来、没召回、排序不对、证据不足、生成错误、误拒答”等具体原因；保留至少三个修复前后的案例。

**4. 沿现有 RAG 链路逐项提升**

| 环节 | 现状 | 优先改进 | 验收示例 |
| --- | --- | --- | --- |
| 文档与加载 | PDF 各页被拼成字符串；DOCX 先收段落再附加表格 | 解析输出文本与页码/章节/顺序；正文和表格按出现顺序保留 | PDF 答案能指出页码，DOCX 表格出现在正确上下文 |
| 清洗与切块 | 统一按字符递归切分 | 按标题、段落、表格边界切分并继承来源；先与当前方法对照 | 选定的问题中，完整步骤或表格行能一起进入上下文 |
| 向量化 | 已有批处理和模型身份校验 | 以用户、内容摘要和处理配置识别重复任务；对可恢复错误有限重试 | 重传同一版本不重复建块；429/超时后能恢复 |
| 存储与更新 | 同步重建；失败文档禁用 | 标记内容版本、切块器版本；新版本准备成功后切换生效 | 更新失败时旧版本仍可用；删除后旧版本不再参与检索 |
| 问题处理 | 每次只有当前问题 | 持久化会话；针对依赖历史的追问做独立问题改写 | “它支持哪些格式”能接上上轮主题，切换话题时不带偏 |
| 召回 | 单路向量召回 | 增加关键词/BM25 召回，融合后使用已有重排 | 同义问题和错误码问题分别比较召回收益 |
| 生成 | 提示词约束 + 引用编号校验 | 传递页码/章节；处理证据不足与冲突；逐事实检查依据 | 含有效引用编号但原文不支持的答案能在评测中被识别 |
| 返回与交互 | 完整答案一次返回 | 先做阶段进度；需要时补 SSE 和断开连接处理 | 用户能知道正在检索/生成，失败后能重试且不重复落库 |

其中页码/章节贯穿解析、切块、存储、检索、响应和前端展示，适合作为第一项完整功能开发。DOCX 的页码依赖排版，不应凭段落数伪造，可以用章节/段落位置定位。

结构化切块先针对现有文档类型做一两种，例如 Markdown 标题和 PDF 页级元数据。OCR 是否优先取决于实际是否需要扫描件；复杂版面和完整表格识别可以后续再补。

关键词召回可先做中文分词后的 BM25 作为实验，再决定持久化索引方案。两路必须共享用户、可用状态、文档版本和向量配置等过滤约束，合并时按块标识去重，用 RRF 等方法融合后交给现有重排。向量相似度和 BM25 分数不在同一个量纲，不能随意直接相加。PostgreSQL 全文检索排序也不等同于 BM25，中文需要实际验证分词。官方依据见 [pgvector 混合检索说明](https://github.com/pgvector/pgvector#hybrid-search)。

当前数据库模型及迁移没有创建 HNSW/IVFFlat 向量索引。先记录数据量和查询耗时，保留精确检索基线；当数据规模或耗时体现出需要时再做 HNSW 实验，使用查询计划验证生效，比较加索引后的速度与召回。带用户过滤时还要检查候选不足，不能只测无过滤的全库查询。参考 [pgvector 索引与过滤说明](https://github.com/pgvector/pgvector#indexing)。

缓存优先考虑同用户、同处理配置下的重复向量化。答案缓存会额外涉及用户权限、文档版本和失效策略，适合稍后再做。

现有答案在生成完成后检查引用。如果直接把原始 token 流推给用户，最终拒答也无法收回已经展示的内容。先提供进度事件和校验后的最终答案；真正流式输出时，明确草稿与最终结果的处理方式，再评估首字延迟和完整回答耗时。

**5. 把同步上传改成可恢复的后台任务**

现有上传请求直接调用 `ingest_document()`，解析和远程向量化期间一直占用请求。建议选择 Celery + Redis：Redis 先作为 Celery 的消息代理，用一个实际场景学习队列与 Worker。

当前开发环境是 Windows。Celery 官方不支持 Windows，Worker 建议运行在 Linux 容器或 WSL2 中，并确保能读取后端保存的同一份上传文件；数据库、队列地址和文件路径需要按各自运行环境配置。参考 [Celery 官方 Windows 支持说明](https://docs.celeryq.dev/en/stable/faq.html#does-celery-support-windows)。

最小流程：上传源文件并创建文档/任务记录 → 数据库事务提交 → 派发任务 → 返回 HTTP 202 与任务/文档标识 → Worker 解析、切块、向量化、写入 → 前端查询阶段与进度。

任务状态可增加排队、解析、向量化、完成、失败；进度按实际页数、块数或批次数计算。数据库保存业务任务状态，避免把 Redis 中短期的任务结果当成唯一事实来源。

任务要能重复执行：相同用户、文件版本和处理配置不重复写入；旧版本任务完成时不能覆盖更新的版本；文档已删除时任务不应重建资料。对超时、429、部分 5xx 做有上限且带退避的重试，对损坏文档、鉴权错误等保留明确失败原因。

派发需要在事务提交后进行。Celery 的 `delay_on_commit()` 不直接返回任务 ID；若接口需要标识，可以先创建业务任务 ID。数据库提交后队列投递失败，还要能把任务标为可重试或由管理命令重新派发。参考 [Celery 官方 Django 集成文档](https://docs.celeryq.dev/en/stable/django/first-steps-with-django.html)。

验收：上传后可关闭或刷新页面；另一个页面能继续查询任务；模拟模型超时后能重试；同一任务执行两次不增加重复块；重建失败不污染旧版本；删除与任务并发有可解释的行为。

**6. 增加一个范围明确的 Agent / 工具调用场景**

保留知识库为主场景，例如“查询某软件错误码的解决办法，同时查询本人提交的故障单当前状态”。制度/手册内容走 RAG，结构化状态走后端查询，能自然说明为什么需要不同工具。

最小工具集可以是 `search_knowledge(query)`、`get_ticket_status(ticket_id)`，以及仅处理明确表达式的计算工具。用测试数据演示即可，工具输入使用结构化参数，后端负责校验。工单查询的用户身份从服务端会话获取，而不是接受模型提供的任意用户 ID。

当前 `QwenChatModel` 只处理文本消息，没有实现 `bind_tools`、`tool_calls` 和工具结果消息的往返；依赖也尚未包含完整 Agent/图工作流框架。第一步要验证当前模型服务支持哪种工具调用协议，并完成适配与往返测试，再选择框架。不能只在现有类外面套 Agent 接口便认为已经支持。

如果当前服务缺少工具调用能力，可以先做结构化意图路由、参数校验、工具执行与回答的工作流，并如实描述为工作流。后续使用支持工具调用的服务后，再加入模型选工具与多步执行。工具调用协议参考链接见来源核对笔记，具体能力以实际使用的服务验证为准。

设置最大工具调用次数、总超时和失败退出方式；工具结果仍需按用户过滤。用固定案例测试选错工具、缺参数、无权限、工具超时和循环调用。

验收：演示直接知识问答、本人业务状态查询、需要两个工具的问题，以及工具失败的处理；能展示工具名、参数摘要、结果和耗时。不要以模型内部推理文本作为必要展示内容。

继续使用 Django，围绕现有栈形成开发经验。按照部署目标补齐前端静态服务/反向代理、Django 应用进程、Worker、Redis 与 PostgreSQL；当前 Compose 只有数据库。补健康检查、部署配置、持久化和备份恢复说明。

在 CI 中执行后端测试、真实 PostgreSQL/pgvector 测试和前端构建。现有测试已经覆盖部分权限与模型适配边界，重点补异步任务幂等、新检索分支的隔离、更新/删除并发，以及一条“登录→上传→等待可用→提问→查看来源”的端到端流程。新增测试应检查行为与边界，而不是重复内部实现。

日常练习读取 Linux 日志、定位端口、排查数据库连接、模型超时和前后端请求错误；整理一两份“现象→假设→证据→修复→回归”的排障记录。项目之外继续准备 Python、SQL、HTTP、Git 和基础数据结构；岗位中的学历、2027 届要求等需要按自己的情况单独核对。

**8. 建议实施顺序与停止标准**

下面按六个阶段排列；可以按周推进，实际时间取决于对现有代码的掌握程度。每阶段先完成可演示的最小闭环。

| 阶段 | 主要工作 | 产出 |
| --- | --- | --- |
| 1 | 选定语料、30 条问题、阶段日志与基线 | 原始结果、耗时表、失败分类 |
| 2 | 页码/章节贯通、结构化切块、扩充评测集 | 可定位来源的界面、切块对照报告 |
| 3 | 关键词 + 向量融合，复用重排，调参并留出验收集 | 检索对比、收益/代价和剩余失败案例 |
| 4 | Celery + Redis、进度、重试、幂等、版本更新 | 长任务演示、失败恢复与并发测试 |
| 5 | 会话持久化、追问处理、一个工具调用场景 | 多轮案例、工具调用记录与边界测试 |
| 6 | Linux 完整部署、CI、接口与架构文档 | 新环境复现说明、演示视频、简历材料 |

针对第一份岗位，可以先以阶段 1–4 加基础部署形成投递材料；第二份增加对 HTTP、Redis、队列和 AI 辅助编程案例的准备；第三份重点展示阶段 5 中工具调用与评测。阶段划分用于安排学习，不能视为招聘通过条件。
